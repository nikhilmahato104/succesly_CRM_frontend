📌 What Did We Build?📌 Humne Kya Banaya?

We implemented a 3-token, 5-layer security architecture for Succesly Admin. This is the same pattern used by Google, GitHub, Stripe, and Notion. No JWT token is stored in any cookie or localStorage — making it invisible to Cookie Editor, XSS attacks, and browser extensions. Humne Succesly Admin ke liye 3-token, 5-layer security architecture implement ki hai. Ye same pattern hai jo Google, GitHub, Stripe, aur Notion use karte hain. Koi bhi JWT token kisi cookie ya localStorage mein store nahi hai — is wajah se ye Cookie Editor, XSS attacks, aur browser extensions ke liye invisible hai.

accessToken

Where: Redux auth.accessToken

Expiry: 15 minutes

JS reads it: ✅ YES (from Redux)

Stored in cookie: ❌ NEVER

Stored in localStorage: ❌ NEVER

csrfToken

Where: Redux auth.csrfToken

Expiry: Same as rt session

Sent on: POST/PUT/PATCH/DELETE

Header: x-csrf-token

Stored in cookie: ❌ NEVER

rt cookie

Where: Browser httpOnly cookie

Expiry: 7 days

JS reads it: ❌ IMPOSSIBLE

Set by: Server only

Sent by: Browser auto (withCredentials)

✅ Golden Rule: Frontend never touches the rt cookie. It never sees it. The browser sends it automatically. The server sets it and clears it. ✅ Golden Rule: Frontend kabhi rt cookie ko touch nahi karta. Usse dikhta hi nahi. Browser automatic bhejta hai. Server set aur clear karta hai.

The Challenge — What Problems Were We Solving?Challenge — Hum Kya Problems Solve Kar Rahe The?

🔴 Attack 1: Fake Cookie Bypass🔴 Attack 1: Fake Cookie Bypass

Any person can open DevTools → Application → Cookies → manually set t = anyrandomvalue → try to access /dashboard/admin. Old system trusted the cookie value blindly. Koi bhi DevTools → Application → Cookies kholke manually t = anyrandomvalue set karke /dashboard/admin access karne ki koshish kar sakta tha. Purana system cookie value ko blindly trust karta tha.

STATUS: SOLVED ✅

🔴 Attack 2: Cookie Theft via Cookie Editor🔴 Attack 2: Cookie Editor se Cookie Chori

Logged-in user opens Cookie Editor extension → exports the JWT token → pastes in another browser → gets full access. The old JWT was stored in a readable cookie — visible to any browser extension. Logged-in user Cookie Editor extension kholke JWT token export karta tha → doosre browser mein paste karta tha → full access mil jaata tha. Purana JWT ek readable cookie mein tha — koi bhi browser extension dekh sakta tha.

STATUS: SOLVED ✅ (accessToken is now in Redux — invisible to extensions)

🔴 Attack 3: CSRF — Cross-Site Request Forgery🔴 Attack 3: CSRF — Cross-Site Request Forgery

A hacker creates a malicious website. When the logged-in user visits it, that website secretly sends API calls (delete user, change role) on behalf of the user. Old system had no CSRF protection. Hacker ek malicious website banata hai. Logged-in user jab us website pe jaata hai, wo website secretly user ke naam se API calls (user delete, role change) bhej deta hai. Purane system mein CSRF protection nahi tha.

STATUS: SOLVED ✅ (csrfToken required on every state-changing request)

🔴 Attack 4: XSS Token Theft🔴 Attack 4: XSS se Token Chori

If any injected JavaScript runs on the page, it can read localStorage and readable cookies. Old system stored JWT in cookie readable by JS → one XSS = complete account takeover. Agar page pe koi injected JavaScript chale, to wo localStorage aur readable cookies padh sakta hai. Purana system JWT ko JS-readable cookie mein store karta tha → ek XSS = complete account takeover.

STATUS: SOLVED ✅ (accessToken only in Redux memory — no XSS can reach it)

CSRF Prevention — How It WorksCSRF Prevention — Ye Kaise Kaam Karta Hai

What is a CSRF Attack?CSRF Attack Kya Hota Hai?

Imagine you are logged into Succesly Admin. A hacker sends you a link — hacker.com/trick.html. When you open it, that page silently sends a POST request to api.succesly.in/users/delete using YOUR session cookies. The server sees a valid session and deletes the user. This is CSRF. Socho tum Succesly Admin mein logged in ho. Hacker tumhe ek link bhejta hai — hacker.com/trick.html. Jab tum use kholte ho, wo page secretly tumhare session cookies use karke api.succesly.in/users/delete par POST request bhej deta hai. Server valid session dekhta hai aur user delete kar deta hai. Ye hai CSRF.

How We Block CSRFHum CSRF Kaise Rokate Hain

Every state-changing request (POST / PUT / PATCH / DELETE) must include the x-csrf-token header. The CSRF token lives only in Redux memory — it is never in any cookie. hacker.com cannot read our Redux state (same-origin policy). No CSRF token = server rejects the request. Har state-changing request (POST / PUT / PATCH / DELETE) mein x-csrf-token header zaruri hai. CSRF token sirf Redux memory mein rehta hai — kisi cookie mein nahi. hacker.com hamaari Redux state nahi padh sakta (same-origin policy). CSRF token nahi = server request reject kar deta hai. 

// identityinstance.ts — Request Interceptor (automatic — developer needs to do NOTHING)
identityInstance.interceptors.request.use((config) => {
  const state      = store.getState();
  const accessToken = state.auth?.accessToken;
  const csrfToken   = state.auth?.csrfToken;

  // Authorization on every request
  if (accessToken && !config.headers["Authorization"])
    config.headers["Authorization"] = `Bearer ${accessToken}`;

  // x-csrf-token ONLY on state-changing methods (not GET)
  const method = (config.method ?? "").toLowerCase();
  if (csrfToken && ["post", "put", "patch", "delete"].includes(method))
    config.headers["x-csrf-token"] = csrfToken;

  return config;
});

Known Issue — SameSite Cross-Origin (Dev Only)Known Issue — SameSite Cross-Origin (Sirf Dev Mein)

⚠️ The ProblemProblem Kya Hai

Frontend: http://localhost:5173 ↔ Backend: https://api.succesly.in — these are cross-origin (different domains). The browser's SameSite policy blocks the rt httpOnly cookie from being sent in cross-origin requests. This causes refresh to fail = user gets kicked to login on page reload during local development. Frontend: http://localhost:5173 ↔ Backend: https://api.succesly.in — ye cross-origin hain (alag domains). Browser ki SameSite policy rt httpOnly cookie ko cross-origin requests mein bhejne se rokti hai. Isse refresh fail hota hai = local development mein page reload par user login page par aa jaata hai.

The Fix (Backend team — Nikhil)Fix Kya Hai (Backend team — Nikhil)

// Current (blocks cross-origin dev):
res.cookie("rt", refreshToken, { httpOnly: true, secure: true, sameSite: "strict" });

// Fix (allows cross-origin with credentials — works in dev + prod):
res.cookie("rt", refreshToken, { httpOnly: true, secure: true, sameSite: "none" });
//                                                                            ^^^^
// One word change. Secure=true is REQUIRED when SameSite=None.
// Since api.succesly.in is HTTPS, this works perfectly.

This is the industry standard setting used by Auth0, Firebase, AWS Cognito, and every API that serves a cross-origin frontend. Without this, the httpOnly cookie architecture simply cannot work for cross-origin dev setups. Ye industry standard setting hai jo Auth0, Firebase, AWS Cognito, aur har wo API use karta hai jo cross-origin frontend serve karta hai. Iske bina httpOnly cookie architecture cross-origin dev setups ke liye kaam nahi kar sakta.
