Booking Parser — System Design & PRD

📁 v2 🗓 May 2026 👤 For new developers joining the project

1 · What this system does

When a CRM agent receives a WhatsApp message from a prospective PG tenant, they paste the raw text into the Create Bookings modal. The system automatically extracts structured fields (customer name, phone, address, etc.) from unstructured free-form text — no manual copy-paste required.

Goal: Turn WhatsApp conversation snippets into clean booking records with as little manual correction as possible.

Data flow

// Agent pastes raw text
"Nikhil Mahato\n9304567655\nIris Tech Park Room 402"

       ↓  parseBookingRawText()

// Structured output
{
  user_name:  "Nikhil Mahato",
  user_phone: "+919304567655",
  address:    "Iris Tech Park, Room 402",
  ...
}

       ↓  POST /api/v1/bookings

// Saved to backend

4 · Algorithm walkthrough

parseBookingRawText(raw) in bookingParser.ts runs five passes in order — each pass fills in fields that earlier passes missed.

Pass 1 — Phone extraction (highest confidence)

// Indian mobile: optional +91/91 prefix, 10 digits starting with 6-9
const PHONE_RE = /(?:\+91|91)?([6-9]\d{9})\b/;

// Handles: "9304567655", "+919304567655", "91 9304 567655"
// Also handles 12-digit mistakes — regex finds first valid 10-digit run

Pass 2 — URL extraction

// Google Maps / live location links
const URL_RE = /https?:\/\/[^\s,\n]+/;

Pass 3 — Labeled field extraction (high confidence)

Structured WhatsApp templates send data with labels. This pass extracts them first.

// Examples matched:
"Name: Nikhil Mahato"         → user_name
"PG Name: Iris Tech Park"     → address (pgName)
"Room No: 402"               → room suffix
"Contact Number: 9304567655"  → user_phone (fallback)
"Live Location: https://..."  → live_location_url

Pass 4 — Sentence pattern extraction (medium confidence)

// Natural language sentences
"My name is Nikhil Kumar"     → "Nikhil Kumar"
"I'm Priya Sharma"           → "Priya Sharma"
"booking for Nikhil Kumar"   → "Nikhil Kumar"
"Mr. Rajesh Singh"          → "Rajesh Singh"

Pass 5 — Line scoring fallback (handles unstructured text)

For plain WhatsApp messages like "nikhil mahato\n9304...\niris tech park":

  1. Split into lines, strip emoji, filter phone-only / URL / room-number-only lines.
  2. Score each remaining line with nameScore().
  3. Highest-scoring line (≥ 3) becomes user_name.
  4. All other lines are combined as address, with location-keyword lines promoted first.

5 · Name-score formula

nameScore(line, isFirstDataLine) returns a number. Lines scoring ≥ 3 are treated as person names; lower scores mean address or garbage.

ConditionScore ΔWhy
Line contains a digit−10Digits → address / room number, never a name
Line contains a URL−10Definitely not a name
Contains location keyword (park, pg, sector…)−8Strong signal this is an address
Contains punctuation (comma, @, #…)−5Punctuation is rare in proper names
Any word is non-alphabetic−5Names are pure letters
Word count ≥ 5−3Too long — likely a sentence
Contains stop-word (here, want, book…)−2Contextual words, not name parts
Exactly 2–3 words+4Ideal Indian name length
Title-case words (Nikhil Mahato)+2Proper nouns signal names
No location keywords(not penalised) Absence of penalty is itself a positive signal
All-lowercase, 2+ words+1Casual WhatsApp typing (nikhil mahato)
First line after filtering+1Names typically come first in messages
Each word 2–15 chars+1Reasonable name length

Location keyword dictionary (partial)

// Structural words
'pg', 'hostel', 'flat', 'room', 'floor', 'wing', 'apartment',
'building', 'tower', 'block', 'society', 'complex', 'phase', 'sector'

// Nature / colour words common in PG names
'park', 'view', 'green', 'blue', 'royal', 'golden', 'iris',
'lotus', 'sunshine', 'river', 'hill', 'valley', 'grand'

// Punjab cities
'jalandhar', 'chandigarh', 'ludhiana', 'amritsar', 'patiala',
'mohali', 'zirakpur', 'kharar'
To add a new city or PG-name keyword: open bookingParser.ts and add the lowercase word to the LOCATION_KW Set. No other changes needed.

9 · Draft & localStorage behaviour

EventDraft action
User types in any fieldSave — auto-save on every entries state change
User clicks ✕ / Cancel → confirmsClear — intentional discard; clearDraft() called
User navigates away (blocker) → leavesKeep — draft stays; restored on next open
Page refresh / tab close → user leavesKeep — beforeunload warns; draft survives in localStorage
All bookings created successfullyClear — clean slate
"Clear draft" button → confirmsClear — manual purge with confirmation

Draft key: booking_creation_draft_v2 in localStorage.

Version bump: if you change the BookingEntry type shape, increment the key to booking_creation_draft_v3 to avoid stale parse errors.

10 · Card exit animation

// EntryAnimWrapper applies CSS transition on maxHeight + opacity
maxHeight: exiting ? "0px" : "800px",
opacity:   exiting ? 0 : 1,
transition: "max-height 380ms cubic-bezier(0.4,0,0.2,1), opacity 280ms ease"

// animateOut() flow:
setExitingIds(prev => new Set([...prev, id]));   // triggers CSS
await new Promise(r => setTimeout(r, 420));         // wait for anim
setEntries(prev => prev.filter(e => e.id !== id)); // remove from DOM
The 420 ms wait is intentionally 40 ms longer than the CSS transition (380 ms) to ensure the animation completes fully before the DOM node is removed.

12 · Adding ML / NLP (future)

Option A — compromise.js (lightweight, in-browser)

// Install
npm install compromise

// Usage in bookingParser.ts
import nlp from "compromise";

function extractNameNLP(line: string): string {
  const doc = nlp(line);
  const people = doc.people().out("array");
  return people[0] ?? "";
}
// Pro: zero server cost, fast, offline
// Con: trained on English — misses Indian names

Option B — Claude API (highest accuracy)

// One API call per ambiguous message
const response = await anthropic.messages.create({
  model: "claude-haiku-4-5-20251001",  // fast + cheap
  max_tokens: 150,
  messages: [{
    role: "user",
    content: `Extract from this WhatsApp message:
- customer_name (person's full name)
- address (PG/building location)
Reply as JSON only.

Message: "${raw}"`
  }]
});
// Pro: handles any language / format
// Con: latency + API cost per message

Option C — Custom classifier (best long-term)

Train a lightweight text classifier (e.g. fastText or ONNX model) on your own collected dataset (see §13). Deploy as a small API endpoint. The frontend calls it only for messages where the rule-based parser is uncertain (nameScore between 1 and 3 = "uncertain zone").

13 · Building a training dataset

Every time an agent corrects a parser output, that correction is gold-label training data.

Step 1 — Collect corrections in your backend

// Add this to the booking POST payload when fields were auto-filled
{
  "raw_text":         "nikhil mahato\n9304...\niris tech park",
  "parser_name":      "nikhil mahato",   // what parser guessed
  "corrected_name":   "Nikhil Mahato",   // what agent typed
  "parser_address":   "iris tech park",
  "corrected_address":"Iris Tech Park"
}

Step 2 — Label schema

ColumnTypeDescription
raw_linestringA single line from the WhatsApp message
labelenumname | address | phone | noise | other
corrected_valuestringThe correct extracted value
booking_idstringReference to the booking record

Step 3 — When you have enough data

With ~500 labelled examples you can train a fastText classifier:

# Install fastText
pip install fasttext

# Training data format (one line per example)
__label__name     nikhil mahato
__label__address  iris tech park
__label__phone    9304567655
__label__noise    please confirm availability

# Train
model = fasttext.train_supervised("data.txt", epoch=25, lr=0.5)
model.save_model("booking_line_classifier.bin")

# Predict
model.predict("nikhil mahato")  # → ('__label__name', 0.94)

14 · Future package recommendations

PackageUse caseWhen to add
compromise English NLP — person detection, place detection When rule-based misses >10% of messages

@anthropic-ai/sdk Claude API for smart field extraction When accuracy is critical and cost is acceptable
fastest-levenshtein Fuzzy match city/area names against known list When agents misspell location names
libphonenumber-js Production-grade phone parsing and formatting When supporting non-Indian numbers or formatting variations
zod Runtime schema validation of parser output When connecting parser to strict API contracts
Current recommendation: Stay with the zero-dependency rule-based parser until you have at least 200 real correction examples. The heuristics cover 90%+ of real WhatsApp formats seen in the wild. Add intelligence incrementally — do not over-engineer before you have data.
Where to start: Add the correction-logging payload to the booking POST request today (§13 Step 1). After 2 weeks of production use you will have 100+ real examples to analyse, and the patterns will tell you exactly what to improve next.
