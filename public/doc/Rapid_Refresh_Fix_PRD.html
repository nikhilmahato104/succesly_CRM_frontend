Refresh Token Reuse Detection — How We Fixed the "User Gets Logged Out on Rapid F5" Bug · My Learning Admin Refresh Token Reuse Detection — "Rapid F5 Marne se User Logout Ho Jaata Tha" Bug Ko Kaise Fix Kiya · My Learning Admin

📌 Bug Summary (One Line)📌 Bug Summary (Ek Line)

When a user rapidly pressed F5 (browser refresh) multiple times, they were automatically logged out and redirected to the login page — even though their session was valid. The root cause was concurrent POST /auth/refresh requests carrying the same refresh token, which triggered the server's Refresh Token Reuse Detection and caused it to nuke the entire session. Jab user rapidly F5 (browser refresh) kaafi baar daba deta tha, to woh automatic logout ho jaata tha aur login page pe redirect ho jaata tha — jabki uski session valid thi. Root cause tha concurrent POST /auth/refresh requests jo same refresh token le jaate the, jis se server ka Refresh Token Reuse Detection trigger hota tha aur poori session nuke ho jaati thi.

Severity: HIGH 🔴 Type: Race Condition Area: Auth / Security Status: FIXED ✅ File: AuthContext.tsx

How The Server Works — RT RotationServer Kaise Kaam Karta Hai — RT Rotation

🔄 Refresh Token Rotation (Standard Security)🔄 Refresh Token Rotation (Standard Security)

The My Learning backend uses Refresh Token Rotation — a standard security practice also used by Auth0, Google, GitHub. Every time you call POST /auth/refresh with a valid rt cookie: My Learning backend Refresh Token Rotation use karta hai — Auth0, Google, GitHub bhi yahi use karte hain. Har baar jab aap valid rt cookie ke saath POST /auth/refresh call karte ho:

Browser ──── POST /auth/refresh ────→ Server (sends rt cookie = OLD_TOKEN automatically) Server checks: 1. Is OLD_TOKEN in the database? → YES 2. Is it expired? → NO 3. Has it been used before? → NO (first use) 4. Mark OLD_TOKEN as USED in DB 5. Generate NEW_TOKEN 6. Store NEW_TOKEN in DB, linked to same user session 7. Return: accessToken + csrfToken + set-cookie: rt=NEW_TOKEN

After this, OLD_TOKEN is permanently invalidated. If anyone tries to use it again, the server knows it was already rotated. Iske baad OLD_TOKEN permanently invalid ho jaata hai. Agar koi phir se use karne ki koshish kare, server ko pata hai ki ye already rotate ho chuka hai.

Refresh Token Reuse Detection — The Security TriggerRefresh Token Reuse Detection — Security Trigger

🛡️ What Is Reuse Detection?🛡️ Reuse Detection Kya Hai?

Reuse Detection is an advanced security mechanism. If an already-rotated (used) refresh token is sent again, it means one of two things: Reuse Detection ek advanced security mechanism hai. Agar ek already-rotated (use ho chuka) refresh token dobara bheja jaaye, to iska matlab do cheez ho sakti hai:

  1. Token Theft: An attacker stole the old token and is trying to use it after the legitimate user already refreshed.Token Theft: Attacker ne purana token chura liya aur legitimate user ke refresh karne ke baad bhi use kar raha hai.
  2. Concurrent Request Bug: (Our case) Multiple page loads fired the same token concurrently — a frontend bug, not an attack.Concurrent Request Bug: (Hamara case) Multiple page loads ne same token concurrently fire kiya — frontend bug tha, attack nahi.

The server cannot tell the difference between these two. So it takes the safest action in both cases: Server dono ke beech difference nahi bata sakta. Isliye woh dono cases mein sabse safe action leta hai:

Server receives request with ALREADY-ROTATED token: ❌ Reuse Detected! 1. Mark this token as COMPROMISED 2. Find ALL tokens in this session family (token lineage tree) 3. Invalidate EVERY token in the family — including the new ones 4. Delete session from database 5. Return 401 Unauthorized 6. Clear the rt cookie via set-cookie with Max-Age=0 Result: User is fully logged out. Even valid new tokens stop working.
ℹ️ Why so extreme? RFC 6819 (OAuth 2.0 Threat Model) recommends this behaviour. If a token is being reused, it might mean it was stolen. Nuking the session prevents the attacker from continuing to use it even if they have a rotated copy. ℹ️ Itna extreme kyun? RFC 6819 (OAuth 2.0 Threat Model) yahi recommend karta hai. Agar token reuse ho raha hai, matlab shayad chori ho gaya ho. Session nuke karne se attacker ko rotated copy milne ke baad bhi koi fayda nahi hota.

Layer 1 — Module-Level In-Flight DedupLayer 1 — Module-Level In-Flight Dedup

How It WorksKaise Kaam Karta Hai

A module-level variable _refreshInFlight holds the currently-running refresh promise. If callRefreshApi() is called a second time while the first call is still in progress, it returns the same promise instead of creating a new network request. Module-level variable _refreshInFlight currently-running refresh promise hold karta hai. Agar pehla call still in progress ho aur callRefreshApi() doosri baar call ho, to ye same promise return karta hai naya network request create karne ke bajay. 

// Module-level — lives in JS module scope, reset on every page load
let _refreshInFlight: ReturnType<typeof callRefreshApiRaw> | null = null;

function callRefreshApi() {
  // Layer 1: if there's already a request in flight, return it
  if (_refreshInFlight) return _refreshInFlight;

  // ... (Layer 2 below)

  _refreshInFlight = (async () => {
    try {
      return await callRefreshApiRaw();
    } finally {
      _refreshInFlight = null; // always clear on done
    }
  })();

  return _refreshInFlight;
}
⚠️ Limitation: This only works within one page load. Each F5 creates a fresh module evaluation → _refreshInFlight = null again. This is why Layer 2 is needed. ⚠️ Limitation: Ye sirf ek page load ke andar kaam karta hai. Har F5 fresh module evaluation create karta hai → _refreshInFlight = null fir se. Isliye Layer 2 zaroori hai.

The Lock-Until LogicLock-Until Logic

const _RT_LOCK_KEY    = "__sc_rt_lock";
const _RT_COOLDOWN_MS = 2000; // 2 seconds > typical API response time

// Inside callRefreshApi():
let waitMs = 0;
try {
  const lockUntil = Number(sessionStorage.getItem(_RT_LOCK_KEY) || 0);
  const now       = Date.now();
  waitMs          = Math.max(0, lockUntil - now);
  // Extend lock window so the NEXT page reload also waits
  sessionStorage.setItem(_RT_LOCK_KEY,
    String(Math.max(lockUntil, now) + _RT_COOLDOWN_MS));
} catch { /* sessionStorage unavailable — skip guard */ }

// Wait if needed, then fire
if (waitMs > 0) {
  await new Promise<void>(r => setTimeout(r, waitMs));
}

// After success: clear lock so normal refreshes don't get penalised
try { sessionStorage.removeItem(_RT_LOCK_KEY); } catch {}

src/context/AuthContext.tsx 
// ✅ AFTER — callRefreshApiRaw (raw) + callRefreshApi (guarded wrapper)

// Raw call — only called by the guarded wrapper
function callRefreshApiRaw() {
  return authAxios.post<RefreshResponse>("/auth/refresh", {});
}

// ─── Two-Layer Rapid-Refresh Guard ───────────────────────────────────────

// Layer 1: module-level — deduplicates within same page load
let _refreshInFlight: ReturnType<typeof callRefreshApiRaw> | null = null;

// Layer 2: sessionStorage — serialises across rapid page reloads
const _RT_LOCK_KEY    = "__sc_rt_lock";
const _RT_COOLDOWN_MS = 2000;

function callRefreshApi(): ReturnType<typeof callRefreshApiRaw> {
  // Layer 1 — within-page dedup
  if (_refreshInFlight) return _refreshInFlight;

  // Layer 2 — cross-page cooldown
  let waitMs = 0;
  try {
    const lockUntil = Number(sessionStorage.getItem(_RT_LOCK_KEY) || 0);
    const now       = Date.now();
    waitMs          = Math.max(0, lockUntil - now);
    sessionStorage.setItem(_RT_LOCK_KEY,
      String(Math.max(lockUntil, now) + _RT_COOLDOWN_MS));
  } catch { /* sessionStorage unavailable — proceed without guard */ }

  _refreshInFlight = (async () => {
    if (waitMs > 0) {
      await new Promise<void>(r => setTimeout(r, waitMs));
    }
    try {
      const result = await callRefreshApiRaw();
      // On success, clear lock so normal refreshes aren't penalised
      try { sessionStorage.removeItem(_RT_LOCK_KEY); } catch {}
      return result;
    } finally {
      _refreshInFlight = null;
    }
  })();

  return _refreshInFlight;
}

// useEffect — unchanged, still calls callRefreshApi()
useEffect(() => {
  if (initRef.current) return;
  initRef.current = true;

  (async () => {
    try {
      const refreshRes = await callRefreshApi(); // ← now guarded ✅
      const { accessToken: newToken, csrfToken } = refreshRes.data.data;
      dispatch(setAuthTokens({ accessToken: newToken, csrfToken }));
      const profileRes = await fetchProfileApi(newToken);
      applyProfile(profileRes.data);
    } catch {
      clearAllAuthState();
    } finally {
      setInitDone(true);
    }
  })();
}, []);
