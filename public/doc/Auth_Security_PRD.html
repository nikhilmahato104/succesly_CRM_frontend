How It's Prevented (Technical Explanation) Ye Kaise Roka Jaata Hai (Technical Explanation)

The 3-Layer Guard System in ProtectedRoute ProtectedRoute mein 3-Layer Guard System

  • 1
    Init CheckInit Check
    When the page loads, initDone starts as false if a cookie exists. ProtectedRoute shows a loading spinner — it does NOT render the dashboard yet. This buys time for the real server verification to happen. Jab page load hota hai, agar cookie exist karti hai to initDone start mein false hota hai. ProtectedRoute ek loading spinner dikhata hai — dashboard abhi render NAHI karta. Ye time deta hai real server verification hone ka.
  • 2
    Server Verification (Re-hydration)Server Verification (Re-hydration)
    AuthContext calls GET /auth/profile using the cookie token. The server validates the JWT signature. A random/fake token has no valid signature → server returns 401. AuthContext cookie token use karke GET /auth/profile call karta hai. Server JWT signature validate karta hai. Random/fake token ki koi valid signature nahi hoti → server 401 return karta hai.
  • 3
    Auto Cleanup & RedirectAuto Cleanup & Redirect
    On 401: cookie is removed, Redux is cleared, isAuthenticated becomes false, initDone becomes true → ProtectedRoute redirects to /login. 401 aate hi: cookie remove ho jaati hai, Redux clear ho jaata hai, isAuthenticated false ho jaata hai, initDone true ho jaata hai → ProtectedRoute /login pe redirect karta hai.

Additional: Client-side JWT Expiry Check Additional: Client-side JWT Expiry Check

Even before hitting the server, we decode the JWT payload and check the exp field. If the token is expired, it is treated as null instantly — no API call needed. A random string like "xyz" is not a valid JWT, so atob() throws → treated as expired → cookie removed. Server hit karne se pehle bhi, hum JWT payload decode karke exp field check karte hain. Agar token expired hai to use turant null treat kiya jaata hai — koi API call nahi chahiye. "xyz" jaisi random string valid JWT nahi hai, isliye atob() throw karta hai → expired treat hota hai → cookie remove ho jaati hai.

// ─── 1. JWT Expiry Check (line ~88) ────────────────────────────────
// Ye function JWT ka exp claim decode karta hai.
// Agar token random string hai to atob() throw karega → return true (expired)
function isTokenExpired(token: string): boolean {
  try {
    const payload = JSON.parse(atob(token.split(".")[1]));
    return typeof payload.exp === "number" && payload.exp * 1000 < Date.now();
  } catch {
    return true; // malformed / random string → treat as expired
  }
}

// ─── 2. Token from cookie — expired ones treated as null ───────────
const rawToken = cookies?.t ? String(cookies.t) : null;
const token = rawToken && !isTokenExpired(rawToken) ? rawToken : null;
const isAuthenticated = !!token;

// ─── 3. initDone starts FALSE when cookie exists ────────────────────
// ProtectedRoute will show loader until server responds
const [initDone, setInitDone] = useState(!token);

// ─── 4. Re-hydration useEffect ──────────────────────────────────────
// Server validate karta hai token — 401 aane par cookie remove ho jaati hai
useEffect(() => {
  if (!token || userData.user_id || initRef.current) {
    if (rawToken && !token) removeCookie("t", { path: "/" }); // stale cookie clean
    setInitDone(true);
    return;
  }
  initRef.current = true;
  fetchProfileApi(token)
    .then((res) => applyProfile(res.data))
    .catch(() => { removeCookie("t", { path: "/" }); }) // 401 → cookie hatao
    .finally(() => { setIsLoading(false); setInitDone(true); });
}, []);

What exactly does the attacker do? Attacker exactly kya karta hai?

  • Logs in with valid credentials → gets a real, signed JWT token stored in cookie t Valid credentials se login karta hai → real, signed JWT token cookie t mein store ho jaata hai
  • Opens Cookie Editor browser extension → clicks Export as JSON Cookie Editor browser extension kholata hai → Export as JSON pe click karta hai
  • Copies the JSON (which contains the full JWT value) → opens a different browser or incognito tab JSON copy karta hai (jisme full JWT value hoti hai) → alag browser ya incognito tab kholata hai
  • Imports the cookie → the browser now has a valid, real JWT in cookie t Cookie import karta hai → browser mein ab cookie t mein valid, real JWT hai
  • Navigates to /dashboard/admin — server accepts the JWT (signature is valid) → FULL ACCESS /dashboard/admin pe jaata hai — server JWT accept karta hai (signature valid hai) → FULL ACCESS
👤 ATTACKER logs in with real credentials → gets valid JWT ↓ 🍪 Opens Cookie Editor → Export JSON → copies JWT value ↓ 🌐 Opens new browser → imports cookie t = <stolen JWT> ↓ ⚛️ AuthContext reads token — isTokenExpired() → false (JWT is real, not expired) ↓ 🌐 Calls GET /auth/profile with stolen JWT ↓ ✅ Server returns 200 — JWT signature IS valid (it's the real token!) ↓ 😱 Attacker gets FULL ACCESS as the original user ❌ NOT BLOCKED (yet)

Why can't the frontend stop this alone? Frontend akela ye kyun nahi rok sakta?

The JWT token is cryptographically valid. It was signed by the server's secret key. The frontend has no way to tell the difference between the original user and someone who copied the cookie — both are sending the exact same token. Only the backend can enforce session binding. JWT token cryptographically valid hai. Ise server ke secret key se sign kiya gaya tha. Frontend ke paas original user aur copy karne wale mein farq karne ka koi tarika nahi hai — dono exactly same token bhej rahe hain. Sirf backend hi session binding enforce kar sakta hai.

Strategy: Short-lived Access Token + HttpOnly Refresh Token Strategy: Short-lived Access Token + HttpOnly Refresh Token

This is the industry standard used by companies like Google, GitHub, and Stripe. Instead of one long-lived JWT (7 days), we use two tokens: Ye industry standard hai jo Google, GitHub, aur Stripe jaise companies use karti hain. Ek long-lived JWT (7 din) ki jagah hum do tokens use karte hain:

Refresh Token 7 days httpOnly + Secure cookie set by server — JavaScript CANNOT read it httpOnly + Secure cookie — server set karta hai — JavaScript PADH NAHI sakta Used silently to get new access tokens when they expire Expire hone par silently naya access token lene ke liye use hota hai JS can't read it

Key insight: Cookie Editor extension can only read cookies that JavaScript can read. httpOnly cookies are set by the server response header — they are invisible to document.cookie and to Cookie Editor. Even if visible in DevTools Network tab, they cannot be exported and re-used because they are bound to the browser session by the server. Key insight: Cookie Editor extension sirf wahi cookies padh sakta hai jo JavaScript padh sakti hai. httpOnly cookies server response header se set hoti hain — ye document.cookie aur Cookie Editor ke liye invisible hoti hain. DevTools Network tab mein dikhein bhi, to export karke reuse nahi ho sakti kyunki server ne unhe browser session se bind kiya hota hai.

Step 2 — Auto Silent Refresh Before Token Expires Step 2 — Token Expire Hone Se Pehle Auto Silent Refresh

src/context/AuthContext.tsx
// ─── Silent refresh: 2 minutes before access token expires ─────────
// Ye user ko logout feel nahi hone deta
useEffect(() => {
  if (!accessToken) return;
  const payload = JSON.parse(atob(accessToken.split(".")[1]));
  const msUntilExpiry = payload.exp * 1000 - Date.now();
  const refreshIn = msUntilExpiry - 2 * 60 * 1000; // 2 min before expiry
  if (refreshIn <= 0) { silentRefresh(); return; }
  const timer = setTimeout(silentRefresh, refreshIn);
  return () => clearTimeout(timer);
}, [accessToken]);

Step 1 — Login Endpoint: Return Two Tokens Step 1 — Login Endpoint: Do Tokens Return Karo

Change POST /auth/login to return a short-lived access token in the response body AND set a long-lived refresh token as a httpOnly + Secure cookie via response header. // Node.js / Express example
// ─── Login route ────────────────────────────────────────────────────
app.post("/auth/login", async (req, res) => {
  // ... validate credentials ...

  const accessToken  = signJWT({ user_id }, "15m");   // short-lived
  const refreshToken = signJWT({ user_id }, "7d");    // long-lived

  // ✅ Refresh token: httpOnly cookie — JS cannot read it, Cookie Editor cannot see it
  res.cookie("rt", refreshToken, {
    httpOnly: true,   // JS nahi padh sakta
    secure:   true,   // HTTPS only
    sameSite: "strict",
    maxAge:   7 * 24 * 60 * 60 * 1000,
  });

  // ✅ Access token: response body — frontend store karega memory mein
  res.json({ success: true, data: { token: accessToken, user: { ... } } });
});

Step 2 — New Endpoint: POST /auth/refresh Step 2 — Naya Endpoint: POST /auth/refresh 

// ─── Refresh route ───────────────────────────────────────────────────
// Frontend page refresh par ye call karega
// Browser automatically httpOnly cookie bhejega — no JS needed
app.post("/auth/refresh", async (req, res) => {
  const rt = req.cookies.rt; // httpOnly cookie automatically aata hai
  if (!rt) return res.status(401).json({ message: "No refresh token" });

  const payload = verifyJWT(rt);
  const newAccessToken = signJWT({ user_id: payload.user_id }, "15m");

  res.json({ success: true, data: { token: newAccessToken } });
});
